# 初心者向けモード（チュートリアル）を他タイトルで設計するときの手引き

MyCryptoSurvivor のストーリーモード（SPEC-165。 EASY = SPEC-147 / 154 / 164 を置き換えた）で分かったことを、
ほかのタイトルの最初のセッションに渡せる形にまとめたもの。 **§1 はそのまま貼る用のプロンプト**、 §2 以降はその根拠と細かい話。

振り返りのスライド（`story-mode-retrospective.html`。 スクリーンショットつき）は作者に別添で渡している。 画面に MCH の絵が入るのでリポジトリには置かない。

## 1. 他セッションの最初に貼るプロンプト

```
このタイトルに「初心者向けモード（チュートリアル）」を入れたい。 先に設計を SPEC に書き、 私の答えを待ってから実装する。
MyCryptoSurvivor のストーリーモード（bearko/MyCryptoSurvivor の docs/specs/SPEC-165-story-mode.md と
docs/process/ONBOARDING_MODE_PLAYBOOK.md）で分かったことを前提にする。 同じ形（ストーリーモード）を
作るのではなく、 このゲームの特性に合った形と長さを選ぶこと。

守る原則:
1. 1 ステップ 1 要素。 そのステップで新しく出るものは 1 つだけ。 それ以外は前のステップまでに出たものだけ。
2. 課題感は小出しに、 報酬は早めに・一気に。 課題感（ストレス）≪≪≪ 報酬。 迷ったら報酬の側に倒す。
3. してほしいことは、 それしか押せない形で出す（ゲート）。 説明の文で分からせない。 スキップは置かない。 1 つ 1 つを短く。
4. 壊れない。 倒れたら同じステップをすぐやり直す。 用意していないものは出ない・落ちない・売らない。
5. 進みは保存し、 タイトルに戻っても続きから。 既に解放済みの人から何も取り上げない（モードのロックは足すだけ）。
6. 本番の仕様（報酬の表・ランキング・RTA・実績）は変えない。 チュートリアル中は共通基盤へスコアを送らない。
7. 文は短く（1 行 2 文まで、 設定用語は 1 行に 1 つ、 最後は次の行動）。 固有名詞は色で目立たせる。 マインちゃんは「私 / あなた」。

作りの決まり:
- ステップは「レシピ」（データ 1 行）で決め、 コードは 1 本。 レシピにあるものだけ出す（features で絞る）。
  クリア条件・出すもの・押させるもの・文・解放・開始状態を 1 行に書く。
- 進みの保存は 1 つのキー（例 <prefix>.story: { cleared, best, bonds, loadout }）。 「どこまで」と「持ち物」を分けて持たない。
- 節目（中ボス・章の終わり）には「越えた瞬間のポップアップ」で報酬をまとめて見せ、 押すまで時間を止める。
- 自動プレイの道具を先に用意し、 1 ステップずつ回して秒数と倒れないことを見る（不慣れ = 被ダメ ×0.5 / ふつう = ×0.3 の 2 水準）。
- 画面ごとに状態の番号（S-01…）を振り、 スクリーンショットで確かめる。 jsdom や hidden クラスだけで判定しない（z-index・外部画像・reduce-motion の差で実機とズレる）。
- 録音は文が固まってから。 文を変えたら必ず「どの録音が食い違うか」を一緒に報告する。
- 実在する他タイトルの名前は GitHub に書かない（「参考作」と書く）。

進め方:
1. まず「このゲームの特性」を 1 枚にまとめる: 1 プレイの長さ、 コアループ、 失敗の重さ、 プレイヤーが選ぶ回数、 本番で初めて出る要素の数。
2. それを踏まえて形を選ぶ（下の表）。 長さは「本番 1 プレイの 1〜2 倍」を上限にし、 最初の 3 ステップは合計 2 分以内。
3. SPEC に「ねらいと守ること」「全体の形」「レシピの型」「ステップの表（何を教える・クリア条件・秒）」「台本」「段取り（1 PR 1 意図）」「確かめ方」を書く。
4. 私が触れる最小の縦切り（最初の章だけ）を先に出し、 遊んだ結果で残りを直す。 1 PR 1 意図、 テスト・自動プレイ・ビルドを通してから報告。
5. 実装の記録（作者の指摘 → 原因 → 直し）を SPEC の末尾に表で残す。

形の選び方（ゲームの特性 → 形）:
- 1 プレイが短く（〜5 分）、 失敗しても失うものが小さい（Survivor・Tactics の 1 戦 など）
  → ステージ制（短い段を一本道で。 Survivor は 5 章 × 5 段 = 25 段、 W1 は 15〜60 秒）
- 1 プレイが長く、 状態が積み上がる（Factory・Portfolio のような経営 / 運用）
  → 「見習い期間」: 本番の最初の N ターン（週・日）を、 出すものと押せるものを絞った同じ画面で導く。 別モードにしない
- 1 プレイがカードや手札の読み合い（DeckBattle・TCG）
  → 台本つきの 2〜3 戦（相手の手札とドローを固定し、 1 戦 1 要素）。 本番のデッキは触らない
- 学習型（Education）
  → 既にある「無説明の初回起動」を保ち、 要素が増える節目にだけ 1 段の案内を置く（説明の画面は作らない）
どの形でも共通: 1 ステップ 1 要素・ゲート・節目の報酬ラッシュ・進みの保存・自動プレイでの確認。

最初に私に聞くこと（推し案を付けて）:
- 形と長さ（上の表のどれか・ステップ数・合計時間）
- 本番のロックをどうするか（初めての人に本番を隠すか）
- 節目の報酬（本番の報酬の表に影響しない範囲で何を渡すか）
- 録音の有無と台本の形式（日本語 1 列の CSV）
- 実績 ID が要るか（共通基盤側の登録は別作業）
```

## 2. Survivor で分かったこと（根拠）

### 2.1 経緯（3 段階）

| 段階 | 何を | なぜ変えたか |
|---|---|---|
| SPEC-146（10/20） | 初めての人は脅威 T0・ショップは 2 回目から・倒れたら木から再挑戦 | 共通基盤のデータで「初めての人の最初の挑戦が 6 分半 → 1〜2 分半に短くなった」と分かった。 ゲームの仕組みを変えてしまい、 作者が却下 |
| SPEC-147 → 154 → 164（10/21〜22） | **EASY**: 短い 3 ステージ → 2 ステージ。 レッスン（止めて読み上げ → 止めずに吹き出し）、 ステージ 2 で負けて木へ、 根で覚醒して勝つ | 「負けて学ぶ」は不慣れな人に重く、 2 ステージに要素を詰めすぎた。 説明が多く、 止めるたびに流れが切れる |
| SPEC-165（10/22） | **ストーリーモード**: 5 ランド × 5 ステージ、 1 ステージ 1 要素、 レシピで強制、 中ボス（シャドー）と絆、 世界観 | 課題と解消のサイクルを短く回せ、 1 行ずつバランスを取れる。 「やって学ぶ」。 EASY は撤去 |

### 2.2 効いた設計

- **レシピ駆動**: 25 ステージを `js/story.js` の 1 行ずつで書き、 戦闘のコードは `features` で絞るだけ。 行を足すのが安く、 自動プレイで 1 行ずつ釣り合いを取れた。
- **ゲート**: 店の `only` / `mustBuy` / `must: ["ban"]`、 パンケーキを取るまでクリアしない `require`、 木の根を取るまで「ステージへ」が押せない `treeFirst`。 「説明しない」を支える。
- **報酬ラッシュ**: 中ボスを越えた瞬間に CE の輪・マジックカード・ハート・ギフト券・GUM を一気に。 相手の絵と一言と報酬を 1 枚のポップアップで、 押すまで止める。
- **進みと持ち物の保存**: `mcs.story.loadout`（ヒーロー・装備・CE・固有スキルの段）。 レシピの開始装備は「底」として重ねる。
- **自動プレイ**: `tools/autoplay/run.mjs --mode story --stage 1-2 --k 0.5`。 被ダメの倍率 K で「不慣れ / ふつう」を分け、 秒数と倒れないことを見た。 `AUTO_LOADOUT` で持ち物を仕込み、 `AUTO_SHOT_BOND` でポップアップを撮る。
- **台本のパイプライン**: 文は `ui.json` に key で置き、 `tools/voice/story-csv.mjs` で 1 列の CSV に。 録音は `tools/voice/build.mjs --story` で key の名前の MP3 に。 文と録音が同じ key で結ばれる。

### 2.3 工数がかかった順

1. **作者のプレイ後の手直し**（PR #217〜#229 の大半）。 10 件 + 4 件 + 5 件 + … の指摘を 1 日で回した。 大物を一気に作った反動。
2. **ワールドマップの演出**（v1 → v2 で 3 PR。 地図・詳細・札の 3 画面、 靄、 塔、 旅の演出）。 「世界がある」見せ方は文より効くが、 作り込みは重い。
3. **EASY の撤去**（197 か所の参照。 名前は残して中身を差し替える判断で収めた）。
4. **台本と録音**（文 229 キー・録音 103 本・差し替え 2 本）。 文を直すたびに録音との食い違いが生まれる。
5. **バランス**（W3〜W5 の中ボスは最初の値で不慣れが倒れ、 1 行ずつ下げた）。

### 2.4 反省（Problem）と次（Try）

| 反省 | 次に |
|---|---|
| 25 ステージを一気に作ってから作者が触ったので、 手直しが 1 日に集中した | **最初の章だけ**先に出して触ってもらい、 その結果で残りを作る |
| 「hidden クラスが外れている」で通した確認が、 実機では z-index の裏で見えなかった（1-1 の札） | 画面の一番上にある要素（`elementFromPoint`）で確かめる。 スクリーンショットを撮る |
| 自動プレイが外部の絵を遮断・reduce-motion で、 旅の演出の有無を見落とした | 確認の環境の差を書き出し、 演出は通常の設定で撮る |
| レシピのボスを `isBoss` が見ておらず、 5-5 のボスが雑魚として出ていた（5 分の時計で終わっていた） | 「既存の表の id を前提にした判定」を grep で洗う。 クリアの条件は自動プレイで「その瞬間」を見る |
| 文を「2 分」に直したあとで録音が「4 分」のままだった | 文を変えるときは録音との食い違いを同じ報告に書く。 録音は文が固まってから |
| 店の「4 つまで」が NORMAL の強さにも効いた（撃破 1,135 → 609） | 本番への副作用は旧ビルドと並べて測り、 作者に数字で判断してもらう（今回はそのまま採用） |
| 「毎ステージ ステージ 1 として始まる」など、 内部の言葉で説明して作者に誤解を与えた | 報告は作者の見える挙動で書く。 内部の仕組みは「なぜ」の 1 行だけ |

### 2.5 流用できるもの（そのまま持っていける）

- 原則 7 つと「形の選び方」（§1）
- レシピの型（`clear` / `spawn` / `features` / `shop.must` / `lines` / `unlock` / `require` / `pre` / `strike` / `pickup`）
- 確認点の書式（番号 + 推し案 + 「1 だけ答えれば残りは推し案で進める」）
- SPEC の末尾の「実装の記録」表（指摘 → 原因 → 直し。 行ごとに PR）
- 自動プレイの考え方（K 係数・1 ステップずつ・持ち物を仕込む・ポップアップを撮る）
- 台本 CSV と録音の取り込み（key 名 = ファイル名）
- 「参考作」の表記ルール
